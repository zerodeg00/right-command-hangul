# F18 전환 직후 첫 글자 보호 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 현재 macOS 기본 F18 전환의 입력감을 유지하면서, 빠른 한영 전환 직후 첫 키가 이전 언어로 처리되는 현상을 해결한다.

**Architecture:** macOS가 입력 소스를 전환하는 현재 경로를 기준으로 삼는다. 먼저 실제 키 누름·뗌 및 입력 소스 변경 시점을 측정한다. 설정 변경만으로 해결되면 거기서 끝내고, 그렇지 않으면 기본 단축키 모드에 선택 가능한 ‘첫 글자 보호’를 추가하는 방향을 검증한다. 보조 기능이 필요한 경우에도 F18은 그대로 macOS에 전달하며 TIS 직접 전환으로 대체하지 않는다.

**Tech Stack:** 기존 Objective-C, AppKit, Carbon TIS, ApplicationServices, IOKit. 새 의존성 없음.

**Spec:** 이 문서의 ‘요구와 근거’. 계획 작성 후 사용자가 시험 구현을 승인했으며, 실행 결과는 아래 기록에 남긴다.

## 요구와 근거

- 사용자 확인: 현재 기본 단축키 방식이 가장 안정적이고 체감상 부드럽다.
- 빠른 타이핑에서 양방향 모두 첫 글자가 이전 언어로 처리된다. 예: `gㅏㄴ영`, `ㅇlfja`.
- 약 1초 기다리면 첫 글자부터 정상이다. 전환 관련 타이밍 문제라는 근거이며, 정확한 지연 구간은 미측정이다.
- 확인된 설정: `MappingEnabled=1`, `NativeSwitching=1`. macOS ‘이전 입력 소스 선택’은 F18이다.
- 기본 모드에서는 앱의 이벤트 탭이 비활성이다. 기존 앱 모드의 입력 보관 코드가 현재 증상을 직접 일으키는 것은 아니다.
- 참고할 과거 로컬 실험: `.worktrees/switch-mechanism/docs/research/switch-mechanism.md`에는 macOS 26.2에서 합성 단축키 주입이 전환을 일으키지 않았던 기록이 있다. 조건이 다른 실험이므로 현재 앱에서의 가능성을 단정하지 않되, 합성 F18 주입을 해결책으로 선결정하지 않는다.

## Global Constraints

- 현재 기본 단축키 방식과 기존 앱 전환 방식을 모두 유지한다.
- 조사 중 사용자의 실행 앱·키 매핑·단축키 설정을 임의로 교체하지 않는다. 비교 실험에서 변경한 값은 보관하고 원복한다.
- 고정 지연값을 임의로 늘리거나 기존 TIS 직접 전환 방식으로 되돌리는 것을 기본 해결책으로 삼지 않는다.
- 문자, 전체 키 코드 이력, 클립보드, 비밀번호를 진단 로그에 저장하지 않는다. 진단은 명시적으로 시작·종료하고 필요한 이벤트 종류와 상대 시각만 남긴다.
- 접근성 권한이 없거나 보안 입력이 활성일 때 보조 기능의 효과를 보장하지 않는다. 가능한 경우 기존 F18 전달 방식으로 동작하며, 이를 메뉴에 표시한다.
- 기존 `.worktrees`의 수정사항은 읽기 참고만 하고 수정·병합하지 않는다. 구현 시 별도 작업 브랜치를 사용한다.

## Review Focus

- 키를 누른 상태에서 다음 글자를 입력하는 경우와, 완전히 뗀 직후 입력하는 경우를 구분한다.
- 입력 소스 변경 알림이 도착해도 실제 텍스트 입력기가 준비됐다고 단정하지 않는다.
- 빠른 연속 전환, 키 반복, Shift·Command 조합에서도 입력 순서·키 누름/뗌 쌍을 보존한다.
- 보안 입력·포커스 변경·권한 해제 시 대기 입력이 다른 입력란으로 넘어가거나 무한 대기하지 않게 한다.
- 보호 기능 끄기·방식 변경·종료 시 예약된 작업이 다음 전환의 입력을 잘못 해제하지 않게 한다.

## Task 1: 실제 입력 순서와 지연 구간 재현

**Files:** 필요할 때만 `tests/diagnostics/native-switch-timing.m` 생성. 결과는 이 문서에 기록한다. 제품 코드는 변경하지 않는다.

**Interfaces:** 기존 `--current`와 macOS 입력 소스 변경 알림을 사용한다. 진단 이벤트는 `trigger-down`, `trigger-up`, `typing-start`, `source-changed`의 상대 시각만 출력한다. 일반 키 코드는 출력하지 않는다.

- [ ] 현재 설정·선택 가능한 입력 소스 수·보안 입력 상태·앱 이벤트 탭 상태를 읽어 기준 상태를 남긴다.
- [ ] 기존 실행 앱과 중복으로 키를 소비하지 않는 임시 관찰 도구를 만든다. 키를 수정하거나 전환을 실행하지 않는다. 단축키 진단 로그 시작·중단을 명시하고 일반 타이핑은 지속 관찰하지 않는다.
- [ ] 실제 키보드로 양방향 각각 ‘짧게 누르고 즉시 입력’, ‘누른 채 입력’, ‘완전히 떼고 즉시 입력’, ‘떼고 1초 후 입력’을 비교한다. 현재 채팅 입력란과 TextEdit의 빈 문서를 사용한다.
- [ ] 첫 글자가 들어간 시점이 F18 뗌 이전인지, 입력 소스 변경 이전인지, 변경 알림 이후인지 분류한다. 측정 수치와 화면 결과를 함께 기록한다.
- [ ] 정확히 두 입력 소스만 활성이고 동작 의미가 동일한 경우에 한해 ‘다음 입력 소스’ 단축키와 비교할 수 있다. 별도의 실험용 설정으로 수행하고 끝나면 원복한다. 이것만으로 반복 재현이 없어지면 코드 추가 없이 설정·README 변경으로 끝낸다.

**완료 조건:** 실제로 잘못 입력된 사례의 이벤트 순서가 기록되고, 키 뗌 지연과 입력기 반영 지연 중 무엇이 관측됐는지 설명할 수 있다. 알림만 보고 문자 처리를 정상이라고 판정하지 않는다.

**Interfaces:** 기존 `event_tap_callback`, `input_source_changed`, `release_held_events`, `stop_event_tap`을 재사용하는 방향으로 검증한다. 기존 직접 전환 분기의 `select_target_source`는 그대로 둔다.

- [ ] Task 1에서 문제가 재현된 순서를 입력 보관·해제 상태의 실패 테스트로 작성하고 `make test`에서 실패를 확인한다.
- [ ] F18 누름·뗌은 macOS에 그대로 전달하고, 그 사이 또는 직후에 들어온 일반 키만 준비 여부에 따라 잠시 보관하는 최소 실험을 한다. F18을 다시 주입하거나 `TISSelectInputSource`를 함께 호출해 이중 전환을 만들지 않는다.
- [ ] 대기 시작은 최초 F18 누름, 정상 해제는 실제 관찰한 전환 상태를 기준으로 한다. 알림 누락·전환 실패에는 유한한 안전 해제가 있어야 한다. 기존 0.25초 값을 정답으로 가정하지 말고 측정 결과와 실제 첫 글자 결과로 판단한다.
- [ ] TextEdit와 채팅 입력란에서 보관한 실제 키의 재전달이 동작하는지 확인한다. 합성 키 전달이 차단되거나 조합 중인 한글이 깨지면 이 방식을 채택하지 않는다.
- [ ] 누락·중복·순서 역전이 사라지면서 체감 지연이 허용 가능한지 사용자와 비교한다. 재현 사례가 해결되지 않으면 대기값을 계속 늘리지 않고 관측 결과와 설계 선택을 다시 검토한다.

**완료 조건:** 핵심 재현 사례의 첫 글자 정확성이 개선됐다는 실기 근거가 있다. 이 단계가 실패하면 Task 3으로 진행하지 않는다.

## Task 3: 검증된 보호 기능 통합과 회귀 확인

**Files:** `src/right-command-hangul.m`, `tests/test-event-kind.m`, `README.md`. 테스트 분리가 실제로 필요할 때만 `Makefile`을 변경한다. 설치·제거 스크립트 변경은 예상하지 않는다.

**Interfaces:** 기본 단축키 모드에 `NativeFirstCharacterProtection` BOOL 설정을 추가한다. 기본값은 `NO`. 메뉴 ‘첫 글자 보호 (접근성 필요)’로 켜고 끈다. 실제 적용 여부와 보안 입력 중 일시 비활성을 표시한다. 기존 `MappingEnabled`, `NativeSwitching` 의미는 유지한다.

- [ ] 테스트를 먼저 추가한다: 보호 끔은 F18·일반 키 통과, 보호 켬은 대기 중 일반 키 누름/뗌의 순서 보존, 재전달 표시 이벤트의 재보관 방지, 연속 F18 입력의 이중 전환 방지, 알림 누락의 유한 해제, 모드 변경·종료 시 이전 타이머 무효화.
- [ ] Shift 대문자·문장부호, 왼쪽 Command 단축키, 키 반복, 키를 누른 상태의 연속 전환을 검증한다. modifier 이벤트 처리 순서도 함께 확인하며, 검증 전 일반 입력 보관을 모든 조합키로 확대하지 않는다.
- [ ] 권한 없음·보안 입력·포커스 이동 시 동작을 정의하고 실기로 검증한다. 보관된 키를 다른 앱/입력란에 늦게 전달하는 경로가 남으면 통합하지 않는다. 보호 불가 상태에서 기존 방식으로 돌아가는지 확인한다.
- [ ] 메뉴 켜기/끄기와 설정 저장·복원을 추가한다. 보호 기능을 끄면 현재 F18 방식으로 즉시 복귀한다.
- [ ] `make all test`, `git diff --check`, `sh -n scripts/install.sh scripts/uninstall.sh`, `plutil -lint app/Info.plist launchagents/com.github.right-command-hangul.plist`를 실행한다.
- [ ] 실기 비교표를 기록한다: 양방향 각각 보호 켬/끔, 채팅/TextEdit, 짧은 누름/키 겹침, 조합 중 전환, 빠른 왕복 전환. 재현 조합별 최소 30회 연속 전환에서 잘못된 첫 글자·누락·중복이 없어야 한다. 이는 시험 범위의 합격 기준이며 모든 앱에서의 무결성을 보장하는 수치는 아니다.
- [ ] 사용자가 같은 문장으로 기존 방식과 비교해 첫 글자 정확성과 입력감을 확인한다. README에는 검증된 결과와 보안 입력 제한만 기록한다.
- [ ] 변경을 리뷰하고 관련 파일만 커밋한다. 설치·푸시는 사용자가 요청한 실행 범위에 따라 진행한다.

## 결정과 중단 기준

추천 실행 순서는 재현 측정 → 설정만으로 해결 가능한지 확인 → 필요할 때만 선택 가능한 첫 글자 보호다. ‘누르자마자 F18 누름/뗌 합성’은 과거 이 Mac에서의 실패 기록 때문에 우선 구현 대상으로 삼지 않는다. 보조 기능이 보안 입력에서도 항상 작동한다는 목표나, 전체 키 입력에 상시 지연을 넣는 방식은 포함하지 않는다.

계획 작성 시에는 제품 코드·사용 중인 앱·시스템 설정을 변경하지 않았다. 이후 사용자 승인에 따라 직접 구현하고 실제 입력 시험을 진행했다. 변경 범위와 검증 결과는 아래 실행 기록을 따른다.

## 2026-11-13 시험 진행 기록

- 사용자 승인: 전환 직후 보호를 실제로 시험하고, 끊기는 입력감이 생기는지 비교한다.
- Ruling: 다른 설정 실험으로 경로를 바꾸기보다 현재 F18 설정에서 선택 가능한 보호를 직접 시험한다. 사용자가 현재 방식의 입력감 유지를 우선했기 때문이다.
- Ruling: 최초 시험에는 추가 고정 대기를 넣지 않는다. 입력 소스 변경 확인 직후 다음 실행 루프에서 해제하고, 알림 누락에 대비해 전환 중에만 5ms 간격으로 현재 소스를 확인한다. 실패 시 기존 250ms 안전 해제는 남는다.
- 원래 계획의 Task 1 정량 측정은 미완료다. 임시 관찰 도구는 문자·키 코드를 기록하지 않으며, 현재까지 유효한 실제 키 표본을 얻지 못했다.
- 보호 기본값은 꺼짐. 기존 앱 전환 방식과 네이티브 기본 경로는 유지한다.
- 단위 검증: 임의의 소스 ID 변경 감지, F18 원본 전달 및 직접 TIS 전환 미발생, 키 반복 억제, Shift/문자 누름·뗌 보관 순서, 재전달 이벤트 재보관 방지, 모드 종료 시 세대 무효화.
- 제품 통합의 합격 판정과 30회 실기 비교는 아직 하지 않았다. 이 변경은 사용자 체감 시험용이다.

### 첫 사용자 시험 결과

- 시험 버전을 설치하고 `NativeSwitching=1`, `NativeFirstCharacterProtection=1`, `MappingEnabled=1`을 확인했다. 메뉴와 실행 프로세스의 이벤트 탭도 활성 상태였다.
- 구버전 cdhash가 남은 접근성 항목을 이 앱에 한해 초기화하고 현재 빌드로 다시 허용한 뒤 시험했다.
- 제한된 45초 관찰에서 13번의 F18 누름·뗌 표본을 얻었다. 입력 소스 알림이 첫 일반 키 이전에 관측된 일부 표본에서는 F18 뗌부터 첫 변경 알림까지 약 26~49ms였다. 이는 IME의 실제 문자 처리 준비 완료 시각을 직접 측정한 값이 아니다. 보호 전·후의 통제된 정량 비교도 아니다.
- 사용자 확인: ‘첫 글자가 정상이고 끊김도 없습니다’. 현재 채팅 입력란에서의 실사용 시험은 통과했다.
- 코드 리뷰에서 앱 전환 시 잘못된 PID로 재전달할 수 있는 경로, 보안 입력 전환 시 남는 대기·눌림 상태를 보완했다. 원래 입력 요소가 바뀌면 키를 재전달하지 않고 경고음과 안내로 재입력을 요청한다. 입력 요소 정보를 얻지 못한 앱에서는 보호 없이 F18을 전달한다.
- 첫 시험 이후에는 같은 바이너리를 유지하며 보호 기능을 켜 둔다. 추가 고정 지연은 없다. 알림 누락 시 250ms 안전 해제는 남아 있어 해당 조건의 끊김 여부는 추가 확인이 필요하다.
- 30회 조건별 반복, TextEdit 비교, 보안 입력 전환과 포커스 변경의 실기는 아직 미완료다. 현재 변경은 시험 브랜치이며 커밋·푸시하지 않았다.

### 저장소 반영 승인

- 사용자가 추가 타이핑에서도 즉시 전환되는 느낌과 부드러운 입력감을 확인하고, 현재 버전의 커밋·푸시를 요청했다.
- 최종 코드 리뷰에서 추가 차단 이슈는 없었다. 설치된 시험 바이너리와 실행 설정은 그대로 유지한다.
- 정식 통합 시험의 모든 조건을 완료한 것으로 취급하지 않는다. 기본값은 꺼짐이며, README의 실험 기능 표시와 미검증 범위는 유지한다.
